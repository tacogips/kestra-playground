# Monorepo Multi-Team Release Methodology Survey

An industry survey of how organizations release independently-owned components from a single
repository, conducted to validate or correct the design in
`design-docs/specs/design-per-category-batch-group-cicd.md`.

## Scope And Method

Surveyed on 2026-08-19: DORA research on branching and delivery performance, the canonical
trunk-based development guidance, monorepo release automation tooling (release-please, Changesets),
affected-graph build tools (Bazel, Nx, Turborepo), GitOps promotion practice (Argo CD, Kargo),
monorepo ownership and governance practice, feature-flag practice, and orchestration-specific
deployment guidance for Airflow, Dagster, dbt, and Kestra. Sources are indexed in
`design-docs/references/README.md`.

The question asked of each source: what is the release unit, what triggers a release, how is change
scope computed, and how are ownership boundaries enforced.

## Findings

### 1. Branching: Trunk-Based Development Is The Consensus

The evidence is unusually consistent. DORA reports elite performers are 3.1x more likely to practice
trunk-based development, and that elite performers meeting reliability targets are 2.3x more likely
to use it. The associated practices are specific and measurable: fewer than three active branches in
the repository, merges to trunk at least daily, and no code freezes or integration phases.

The most commonly cited obstacle is not tooling but an overly heavy review process requiring multiple
approvals before merge, which pushes teams back toward long-lived branches.

This validates a single `main` and refutes long-lived per-team branches independently of any monorepo
consideration.

### 2. Release Unit: Per-Component Tags, Generated Rather Than Hand-Managed

The dominant pattern for independently released components in one repository is a per-component
version and a per-component git tag, generated by automation from commit history rather than chosen
by hand.

`release-please` (Google) in manifest mode is the widely used implementation: Conventional Commits
determine the semantic version bump, each component is tracked independently in a manifest,
`monorepo-tags` produces a distinct tag per component, and a standing release pull request
accumulates the changelog until a human merges it, which is the release action. Changesets fills the
same role in the JavaScript ecosystem.

Microsoft's ISE engineering blog documents this exact shape: one directory per project with its own
`CHANGELOG`, manifest-driven release-please, per-project deploy workflows keyed off
`<project>-release_created` and `<project>-tag_name` outputs, and internal dependencies expressed as
version ranges so components need not release in lockstep.

The significant detail is that **merging the release pull request is the release trigger**. The
release is human-initiated and per-component, but the version, tag, and changelog are machine-
generated. This preserves an auditable per-component release unit without hand-typed tags.

### 3. Change Scoping: Dependency Graph Where It Is Affordable, Path Filters Otherwise

Two tiers exist in practice:

| Tier | Mechanism | Typical adopter |
|------|-----------|-----------------|
| Graph-based | Bazel, Nx `affected`, Turborepo filtering compute the dependency graph and act only on affected targets | Google-scale multi-language repositories; Nx for up to several hundred packages; Turborepo as the common JavaScript default |
| Path-based | CI path filters or a diff-to-directory mapping | Everything smaller, including most polyglot infrastructure and data repositories |

Graph-based scoping is strictly more correct, because it catches transitive dependents that a path
filter misses. It costs a build-system migration. The honest industry position is that path-based
scoping is proportionate until either the repository is large enough that CI time dominates, or the
dependency graph is deep enough that "changed directory" stops predicting "affected component".

### 4. Ownership: Layered CODEOWNERS, Platform Team Owns The Shared Surface

The consistent pattern is a layered ownership model: a platform team owns foundational and shared
components, feature teams own their own directories, and `CODEOWNERS` binds those boundaries to
required review. Recommended practice is to start coarse (whole apps or services) and refine toward
per-component ownership as teams specialize, rather than beginning with fine-grained rules.

The broader framing from platform engineering is "golden path" governance: compliance, access
control, and audit are embedded in the reusable template and the paved pipeline, so teams following
the path are compliant by construction rather than by inspection. Governance becomes a property of
the path instead of a gate placed in front of it.

### 5. Promotion: Immutable Artifact, And Promotion Separate From Deployment

GitOps practice converged on promotion as a distinct layer from deployment. Argo CD reconciles the
desired state within an environment; it has no opinion on how an artifact moves between environments.
Kargo and comparable promotion engines fill that gap, modeling an immutable snapshot of artifact
versions (image digest, chart version, git commit) that is promoted stage to stage.

Two properties recur across all descriptions: the promoted thing is immutable and identified by
digest or tag rather than rebuilt per environment, and every promotion is a commit, so every rollback
is a revert and the deployment history lives in version control.

### 6. Hotfix: Roll Forward First, And Fixes Flow Trunk To Branch

This finding contradicted the design under review and is the most important result of the survey.

Canonical trunk-based development guidance is that release branches are created "only when necessary,
on incompatible policy, late, and instead of freeze". When one exists, the fix direction is strictly
unidirectional: **reproduce the bug on trunk, fix it on trunk with tests, verify in CI, then
cherry-pick that commit to the release branch**. Fixing directly on the release branch is explicitly
identified as the failure mode, because the backport to trunk is forgotten and the bug returns to
production weeks later.

Release branches persist only while release activity continues, are then deleted as tidying, and are
never merged back to trunk. Released commits are tagged before deletion so the released code is not
garbage collected.

Continuous delivery teams bypass release branches entirely and roll forward from trunk.

### 7. Decoupling Deployment From Release

Feature flags are the standard mechanism for shipping code to production in a disabled state and
enabling it separately. Martin Fowler's toggle taxonomy classifies flags by lifetime and by who owns
removal, and the commonly forgotten half of the practice is retiring the flag once the decision is
permanent.

The relevance to trunk-based development is direct: flags are what make it possible for in-progress
work to sit on a trunk that must remain releasable at any moment.

### 8. Orchestration-Specific Practice

For data orchestration specifically, the recurring pattern is separating the workflow-definition
deploy from the runtime-image deploy so they have independent cadences and different blast radii. A
broken image then fails specific tasks rather than the orchestrator, and definition changes deploy
without touching the running cluster.

Kestra's own guidance matches the design under review. The CLI form is
`kestra flow namespace update <namespace> <directory>`, and Kestra publishes official
`kestra-io/validate-action` and `kestra-io/deploy-action` GitHub Actions. The deploy action takes
`namespace`, `directory`, `resource`, and `server`, accepts exactly one namespace per invocation, and
its `delete` input **defaults to true**, removing server-side resources absent from the directory.
The CLI equivalent opts out with `--no-delete`.

## Convergent Reference Model

Synthesizing the sources, the modern mainstream model for a multi-team monorepo with independent
component releases is:

1. One trunk. No long-lived per-team or per-component branches.
2. One directory per component, with `CODEOWNERS` binding the directory to its owning team and a
   platform team owning the shared surface.
3. Change scope computed automatically, by dependency graph at scale and by path mapping otherwise.
4. Continuous integration to trunk; trunk always releasable; feature flags carry incomplete work.
5. Automated per-component versioning and tagging from commit history, with a human merging a
   generated release pull request as the release action.
6. An immutable artifact promoted across environments, never rebuilt per environment; promotion
   recorded as a commit.
7. Declarative, scoped deployment where the repository directory is the source of truth and
   server-side drift is removed.
8. Roll forward or roll back by default. Release branches only under an incompatible-release policy,
   fixed on trunk and cherry-picked into the branch, deleted when the line retires.

## Fit Assessment Against The Current Design

| Practice | Reference model | Design under review | Verdict |
|----------|-----------------|---------------------|---------|
| Branching | Single trunk, no long-lived branches | Single `main`, short-lived branches, explicit rejection of per-category branches | Aligned |
| Ownership | Layered `CODEOWNERS`, platform owns shared | Per-directory `CODEOWNERS`, platform owns `_shared/` and CI | Aligned |
| Release unit | Per-component tag | Per-category tag `<group-id>/v*` | Aligned |
| Tag creation | Generated by release automation from Conventional Commits | Hand-cut tags | Diverged; adopt release-please |
| Change scope | Graph-based at scale, path-based otherwise | Path-based `detect` script | Aligned and proportionate at this size |
| Deployment | Declarative, scoped, source-of-truth wins | Namespace-scoped bulk update with deletion | Aligned; tooling detail was wrong |
| Deploy tooling | Vendor-official actions where they exist | Hand-rolled `curl` | Diverged; adopt the official Kestra actions |
| Promotion | Immutable artifact, not rebuilt per stage | Tag points at an already-built commit | Aligned |
| Hotfix direction | Fix on trunk, cherry-pick to release branch | Fix on release branch, forward-port to trunk | **Contradicted; corrected** |
| Rollback preference | Roll back or roll forward before branching | Rollback preferred, then release branch | Aligned |
| Deploy/release decoupling | Feature flags | Not addressed | Gap; added |

## Corrections Applied To The Design

1. **Hotfix direction reversed.** Path 3 now reproduces and fixes the bug on `main`, then
   cherry-picks the commit onto `release/<group-id>/<line>`. The previous "fix on the branch, then
   forward-port" is the exact anti-pattern the trunk-based guidance names. This also removes the need
   for a forward-port pull-request gate, because the fix is on trunk before the release branch ever
   receives it; the enforcement instead becomes a check that release-branch commits are cherry-picks
   of commits reachable from `main`.
2. **Kestra deletion semantics corrected.** Deletion of absent resources is the default, not an
   opt-in flag. The design now uses the official `kestra-io/validate-action` and
   `kestra-io/deploy-action` rather than hand-rolled `curl`, noting that the action accepts exactly
   one namespace per invocation, which fits the per-group matrix precisely.
3. **Release automation adopted.** Per-category tags are generated by manifest-mode release-please
   with per-component tags, and merging the generated release pull request becomes the production
   release trigger, replacing hand-cut tags.
4. **Deploy/release decoupling added.** Flows may be deployed inactive and enabled separately, which
   is the orchestration analogue of a feature flag.

## Deliberate Divergences

| Divergence | Reason |
|------------|--------|
| Path-based change detection rather than Bazel or Nx | The repository is Python and YAML with a shallow dependency graph. Graph-based scoping would cost a build-system migration for correctness this repository can obtain from a directory mapping plus the `_shared/` fan-out rule. Revisit if `_shared/` grows deep enough that "changed directory" stops predicting "affected group". |
| Staged-content hash gate | No surveyed source describes this. It exists because staging deploys only changed groups, so commit-SHA equality cannot express "this content was staged". It is bespoke code rather than configuration and carries correspondingly higher maintenance risk. |
| Namespace-scoped declarative deploy instead of a GitOps controller | Kestra's namespace update with default deletion already provides desired-state reconciliation for flows. Introducing Argo CD or Kargo for flow definitions would add a second control plane for a resource Kestra already reconciles. |
